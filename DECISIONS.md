## D-001: Validate the tunnel with a sphere before trusting other results

- Date: 2026-10-25 (original README)
- Question: How do we know the tunnel and its instruments read true?
- Decision: Measure the drag coefficient of a sphere and compare it with the published value (about 0.47) before any
  other testing. This comparison is the project's headline deliverable.
- Rationale: A known-answer check of the whole chain (airspeed, force, data reduction). The owner's analogy: the 100 MΩ
  reference resistor used to check the STM.
- Alternatives considered: not recorded.
- Evidence / source: original README.
- Status: Accepted. Open detail: the reference Cd must be matched to the test Reynolds number
  ([PROJECT_BACKGROUND.md](PROJECT_BACKGROUND.md#why-reynolds-number-matters-for-the-validation-standard)).
  **2026-11-02: the comparison value "about 0.47" is superseded by D-009** (Brown and Lawler Eq. (19) at each run's
  Re, with a ±10 % band and a trend check). Validating with a sphere still stands.

## D-002: Pitot tube + differential pressure sensor for airspeed; load cell + HX711 for drag

- Date: 2026-10-25 (original README)
- Question: How are airspeed and drag measured?
- Decision: Airspeed from a pitot tube read by a differential pressure sensor; drag from a load cell read by an HX711,
  with signal conditioning from the owner's ECE kit (LM741/LM348, LM317).
- Rationale: Low-cost, buildable instrumentation the owner controls end to end.
- Alternatives considered: not recorded.
- Evidence / source: original README hardware list.
- Status: Accepted as the approach. Specific parts (sensor ranges, load-cell capacity, microcontroller) are **not
  chosen**; see open questions in [PROJECT_STATUS.md](PROJECT_STATUS.md). Note 2026-11-09: the specific parts were
  chosen by the owner on 2026-11-08 in [docs/buy_list.md](docs/buy_list.md) (one SDP810-125Pa, TAL221 100 g load
  cells, a SparkFun HX711; the Elegoo Mega 2560 as the candidate board). The ECE kit's role is open question 2 (proposed:
  the interface board, not the measurement chain). The approach itself is unchanged.

## D-004: Data management: raw data immutable; videos external; no Git LFS yet

- Date: 2026-10-29
- Question: Where do raw data, processed data and large binary files live?
- Decision: `data/raw/` is never edited and is stored byte-for-byte (no line-ending conversion); `data/processed/` is
  regenerated by scripts in `analysis/`; CSV logs are committed directly; videos are kept out of Git and referenced from the
  data catalog; photos are compressed before committing; Git LFS is **not** enabled until a real need appears
  (e.g. CAD files over ~25 MB). Details: [data/README.md](data/README.md).
- Rationale: The expected sensor logs are small text files. LFS adds a dependency for every clone and counts against
  GitHub storage and bandwidth quotas, which is not justified before any large file exists. Video is the only
  foreseeable file type that would exceed GitHub's 100 MB limit.
- Alternatives considered: enable LFS now for images and CAD (deferred); commit everything (rejected: size limits);
  keep all data outside Git (rejected: breaks reproducibility of the analysis).
- Evidence / source: no data or binary files exist yet (inspected 2026-10-29).
- Status: Tentative. A default chosen by the setup agent. Owner to confirm; revisit when the first CAD files or videos exist.

## D-005: Print the tunnel in segments on the Bambu Lab P1S

- Date: 2026-10-30
- Question: How are tunnel parts larger than the P1S build volume (256 × 256 × 256 mm, manufacturer spec) made?
- Decision: The tunnel will be "decently big" (owner's words; test-section size not yet chosen). Parts that do not
  fit the build volume, starting with the contraction, are printed in segments. Segments get alignment holes (for
  pins or dowels) and are joined, probably with glue.
- Rationale: A one-piece printed contraction would cap the test section at about 100 mm, which gives a sphere drag of
  about 1 gf at 10 m/s ([PROJECT_BACKGROUND.md](PROJECT_BACKGROUND.md#printable-contraction-sizes)). A larger tunnel
  gives larger forces, which are easier to measure.
- Alternatives considered: a one-piece print with a ~100 mm test section (rejected: forces too small).
- Design considerations [Proposed, not decided]: keep internal steps at joints as small as possible, and keep joints
  away from the contraction exit, where the flow is fastest and the boundary layer thinnest. The contraction-design
  method in [Bell1988](resources/notes/Bell1988.md) assumes smooth walls with a laminar boundary layer from the inlet.
  Seal seams against leaks. Unknown: filament, wall thickness, segment layout, adhesive.
- Evidence / source: owner statement, 2026-10-30 session.
- Status: Accepted (segmented printing with alignment holes). Joining method (glue): Tentative, then **superseded by
  D-013** (bolted flanges, owner, 2026-11-09). Tunnel size: the
  "decently big" intent is superseded by D-008 (100 mm test section, 2026-11-01). Segmented printing still applies,
  because the 250 mm settling chamber and contraction inlet leave no room for walls and flanges on the 256 mm bed.

## D-007: Open-circuit blower tunnel, fan at the front

- Date: 2026-11-01
- Question: Blower (fan at the front, pushing) or suction (fan at the back, pulling)? And is there an exit diffuser?
- Decision: An open-circuit **blower**: "The fan will go at the front. That will be better" (owner). Proposed layout
  (agent): fan → flexible coupling → short wide-angle diffuser with screens → settling chamber (honeycomb + screens) →
  contraction → closed test section → **open exit, no exit diffuser**.
- Rationale:
  - The test section sits near room pressure, so print seams and the sting slot barely leak (the agent's lean since
    2026-10-31).
  - The honeycomb and screens remove the fan's swirl before the test section.
  - The open exit is the agent's proposal. An exit diffuser by Mehta1979's rule (5°, area ratio 2.5) would add about
    7.5 × the test-section height, about 0.75 m at 100 mm, against the owner's target of a tunnel about 1 m long. It
    would roughly halve the fan pressure and power
    ([PROJECT_BACKGROUND.md](PROJECT_BACKGROUND.md#fan-requirement-estimates)).
- Alternatives considered: suction, the shape of the owner's first sketch
  ([docs/sketches/](docs/sketches/README.md)). The fan's turbulence leaves out of the back, and the sketch's sealed
  electronics box under the floor would stop air leaking in through the sting slot. It needs calm room air at the
  inlet and a square-to-round transition before the fan. An exit diffuser is the other alternative: less fan power,
  more length.
- Consequences: the tunnel will not draw mist in by itself, so optional visualization injects mist after the last
  screen ([TODO.md](TODO.md) P2). The settling chamber runs above room pressure, so any removable panel there needs
  latches or strong magnets.
- Evidence / source: [2026-11-01 session log](docs/sessions/2026-11-01-parts-review-and-kit-inventory.md).
- Status: Accepted (blower, fan at the front; owner). Open exit: Tentative (agent's proposal, not objected to, not
  confirmed).

## D-008: 100 mm × 100 mm test section

- Date: 2026-11-01
- Question: What test-section cross-section? It sets the tunnel length, the sphere size, the drag force and the fan.
- Decision: A square 100 mm × 100 mm test section ("lets keep it at 100mm", owner). The owner first targeted about
  1 m in total including the fan, then allowed more ("we can also go more than 1m if needed").
- Rationale (the comparison shown to the owner; estimates, not measurements,
  [PROJECT_BACKGROUND.md](PROJECT_BACKGROUND.md#tunnel-length-budget)):
  - about 1.15–1.3 m long including a 6-inch fan, close to the owner's 1 m target;
  - one 6-inch inline fan should reach about 13 m/s;
  - the smallest fan, print and parts cost of the sizes compared.
- Alternatives considered:
  - 80 mm, which fits 1 m including the fan but has smaller forces;
  - 150 mm (about 1.6–1.9 m, about twice the force, an 8–10 inch fan);
  - 200 mm (about 2–2.5 m, about four times the force, a 10–12 inch fan, a 500 mm settling chamber in many printed
    pieces). The owner raised 200 mm, then chose 100 mm.
- Consequences:
  - The sphere is about 20 mm at 3 % blockage (25 mm at 5 %). Its drag is about 0.9 gf at 10 m/s and 2.0 gf at
    15 m/s (estimate), so the load cell, its zero drift and the sting drag are the hardest part of the project.
    D-005 had rejected a ~100 mm section for this reason; the owner chose it after seeing the force comparison.
  - Re for a 20 mm sphere is about 1.3×10⁴ at 10 m/s, inside the subcritical C_D plateau.
  - Proposed, not decided: contraction ratio 6.25 (250 mm settling chamber), test section 270–290 mm long.
- Evidence / source: [2026-11-01 session log](docs/sessions/2026-11-01-parts-review-and-kit-inventory.md).
- Status: Accepted (100 mm × 100 mm cross-section; owner). Contraction ratio and section lengths: Tentative.

## D-009: Sphere validation reference: Brown and Lawler Eq. (19) at each run's Re, ±10 % band, plus a trend check

- Date: 2026-11-02
- Question: What is the measured sphere C_D compared with? D-001 said "about 0.47", but the planned test Re is about
  1.3–2.5×10⁴ (20–25 mm spheres at 10–15 m/s), and published C_D changes with Re in that range.
- Decision:
  - Compare each run's corrected C_D (blockage and sting drag removed) with Brown and Lawler (2003) Eq. (19), evaluated
    at that run's Re: C_D = (24/Re)(1 + 0.150 Re^0.681) + 0.407/(1 + 8,710/Re).
  - The reference band is about **±10 %**.
  - Runs at several speeds must also show C_D rising with Re as Eq. (19) predicts: about 12 % from Re = 6.6×10³ to
    2.5×10⁴.
  - The band may be tightened later if the original data tables near Re = 10⁴ are obtained.
- Rationale:
  - Eq. (19) is fitted to 480 curated, wall-corrected sphere-drag points. The selection independently excluded
    Roos1971's vibration-affected points above Re = 5,500. It is an explicit formula the analysis script can evaluate
    for every run.
  - Eq. (19) gives 0.42–0.445 for the planned runs. Its own Fig. 3 data sit about 7 % above it at this Re, with about
    ±8 % scatter (our pixel measurement, axes checked against the Stokes region). The paper's "81 % within ±5 %" is an
    average over all Re, so ±10 % is the honest band here.
  - A single number cannot serve, because C_D rises about 12 % across the test range. The trend check gives evidence
    that does not depend on the absolute band.
- Alternatives considered:
  - A single value of 0.47 (Hoerner, used by Weakly2024). It ignores the Re dependence; it falls inside the band, but
    only at the top of it.
  - Morrison2013 Eq. (1): 7–11 % below Eq. (19) and the data at this Re.
  - Eq. (19) with ±5 % and Clift et al. (1978) as a cross-check, the agent's first proposal. Rejected: ±5 % is too
    tight at this Re, and Clift was fitted to almost the same data, so it is not independent.
  - Roos1971 Table 1: its points at this Re read high, per its authors.
- Evidence / source: [Brown2003 notes](resources/notes/Brown2003.md), [Morrison2013 notes](resources/notes/Morrison2013.md),
  [Roos1971 notes](resources/notes/Roos1971.md); this session's log (2026-11-02).
- Status: Accepted (owner, 2026-11-02, choosing the ±10 % + trend version over the ±5 % + Clift version).

## D-010: Design top speed 13 m/s; validation runs from about 6.5 m/s

- Date: 2026-11-08
- Question: What top airspeed is the 100 mm tunnel designed for? It sets the fan, the pressure-sensor range and the
  force available (open question 3).
- Decision: A design top speed of **13 m/s** in the test section, with sphere validation runs from about 6.5 m/s
  upward. Owner: "the 13m/s top speed is a big priority" (2026-11-08), and the fan was chosen on that basis (D-011).
- Rationale (the agent's 2026-11-05 trade-off; estimates,
  [PROJECT_BACKGROUND.md](PROJECT_BACKGROUND.md#top-speed-trade-off-proposed)):
  - D-009's trend check gains little above it: Eq. (19) rises 8.7 % from the 20 mm sphere at 6.5 m/s to the 25 mm
    sphere at 13 m/s, and 9.8 % at 15 m/s;
  - one 6-inch fan listing about 500 Pa should just reach it;
  - q = 101 Pa fits a ±125 Pa pressure sensor (full scale at 14.4 m/s);
  - below about 6.5 m/s the 20 mm sphere's drag is only 0.2–0.3 gf, so fixed zero errors dominate.
- Alternatives considered: 11–12 m/s (smaller fan, about 30 % less force); 15 m/s (about 35 % more force, 1.5× the
  fan power, an 8-inch fan or two fans, a ±249 Pa or ±500 Pa sensor); 20 m/s.
- Consequences: pressure-sensor range ±125 Pa (SDP810-125Pa proposed). The real top speed is measured with the pitot
  once the tunnel runs. If the fan reaches only about 12 m/s, the validation still works with less force.
- Evidence / source: [2026-11-07 session log](docs/sessions/2026-11-07-top-speed-and-fan-search.md); owner's
  statement in the 2026-11-08 session.
- Status: Accepted (owner, 2026-11-08). Note 2026-11-09: the owner asked whether 13 m/s is a must-have. The agent's
  answer: no. The validation works at 11–12 m/s, with less force (71 % at 11 m/s) and a smaller C_D rise for the
  trend check (7.8 % against 9.2 %). If the VEVOR fan is chosen (D-011, reopened), the top speed becomes whatever it
  reaches, about 11 m/s by estimate.

## D-013: Section joints: bolted flanges, M3 screws into brass heat-set inserts, screens clamped between

- Date: 2026-11-09
- Question: How do the printed sections join? D-005 left the joining method as "probably glue" (Tentative); the buy
  list proposed bolted flanges on 2026-11-09.
- Decision: Every section joint is a bolted flange. An M3 screw passes through one section's flange into an M3 brass
  heat-set insert in the next section's flange. Where a screen sits at a joint, it is clamped between the two flanges
  and the screws pass through it; joints without a screen are bolted the same way. Owner's sketch: "Each section, with
  a screen or not, will be connected like this" (2026-11-09). Asked the same day, the owner kept the buy list's foam
  tape between the faces and the printed two-part screen frames (the sketch shows neither).
- Rationale: the joints come apart, so screens can come out for cleaning (Mehta1977 clamps screen frames with
  drawbolts). Heat-set inserts survive repeated assembly where printed threads would wear. Foam tape seals printed
  faces that are never perfectly flat; a frame keeps the mesh taut and comes out in one piece.
- Alternatives considered: glue (D-005); M4 bolts (buy list §2); flanges touching directly with the bare mesh clamped
  between them (as sketched).
- Consequences: screw length (the owner's "M3 length TBD"), flange width and thickness, bolt count and pitch, insert
  length and pin size are set at sizing. Alignment pins (D-005) keep the inside faces flush; joints stay away from the
  contraction exit (D-005 notes).
- Evidence / source: the owner's sketch,
  [docs/sketches/2026-11-09_flange-load-cell-test-chamber-notes-1.pdf](docs/sketches/README.md), and answers in the
  [2026-11-09 drawing-package session](docs/sessions/2026-11-09-drawing-package.md); [buy list](docs/buy_list.md) §2;
  drawing sheet 10 in [docs/drawings/](docs/drawings/README.md).
- Status: Accepted (owner, 2026-11-09). Supersedes D-005's joining method. Sizes Proposed or TBD.

## D-015: Sting mount and thumb-screw sting lock; no separate hold-still pin

- Date: 2026-11-09
- Question: How is the sting held on the load cell without glue, and how is the 100 g cell protected during model
  swaps (open question 12)?
- Decision: A printed **sting mount** is screwed to the load cell's top end. The 1/8 in brass sting stands in a hole
  facing up, and a hand screw in a perpendicular hole clamps it without glue, "similar to the knob at the top of a
  caliper that locks it in place" (owner, 2026-11-09). The owner calls this the **sting lock**. To swap balls or take
  out the sphere insert, loosen it and lift the sting out. The separate hold-still pin planned since 2026-11-01 (a
  clamp or pin holding the sting during swaps, removed before running) is **dropped** (owner, 2026-11-09, when asked).
  The overload stops (about 120 g) stay.
- Proposed details (agent, 2026-11-09; not decided):
  - a blind hole, so the sting bottoms out and the ball height repeats;
  - the screw threads into a brass M3 heat-set insert, not into printed plastic;
  - a brass (non-magnetic) screw: a printed knob on a brass M3 screw (buy list §2, no extra cost), or a bought
    knurled brass thumb screw (price not checked);
  - the screw axis along the wind, so any twist that gets past the hand bends the cell sideways, its stiff direction
    (if the sensitive axis is as assumed in the [TAL221 notes](resources/notes/TAL221.md));
  - hold the mount with the other hand while turning the screw; finger-tight is enough.
- Rationale: no glue; the sting comes out whole, so balls are changed away from the cell instead of being pushed onto
  it in place, which could exceed the cell's 150 g safe overload.
- Alternatives considered: a printed sting clamp plus a separate hold-still pin (TODO P1, 2026-11-01); glue.
- Consequences: "sting lock" now means this clamp in all docs. The ball stems and sleeve (buy list §6) and the
  calibration attachment (§9) are unchanged; during calibration the pan is hung gently and the stops catch an

- Evidence / source: the owner's sketch ("Load cell notes") and statements, 2026-11-09
  ([sketches](docs/sketches/README.md), [session log](docs/sessions/2026-11-09-drawing-package.md)); drawing sheet 8

## D-018: Sensor interface circuit: laptop USB power, one shared I²C bus, HX711 on pins 2 and 3, shield PCB later

- Date: 2026-11-17
- Question: How do the SDP810, the BME280 board and the HX711 connect to the Mega, what powers them, and what
  becomes the PCB? The owner asked for a walk-through of the circuit once every ordered part had arrived.
- Decision (agent's design, drawn as sheets 11 and 12 of the drawing package, revision D):
  - Power: the laptop's USB port is the only supply for the electronics. The Mega's 5V pin feeds every sensor (about
    100 mA in all against 500 mA available, estimate). The fan keeps its own mains supply (D-012).
  - The SDP810 (0x25) and the Waveshare BME280 board (0x77, ADDR and CS left open) share the I²C bus on Mega pins 20
    (SDA) and 21 (SCL), at 100 kHz.
  - The HX711's DAT and CLK go to digital pins 2 and 3; its VCC and VDD both to +5 V; the load cell is soldered straight
    to it (red E+, black E−, white A−, green A+).
  - C1, 0.1 µF, across the SDP810's VDD and GND pins; C2, 10 µF, where 5 V enters the board. I²C pull-ups R1 and R2
    (5.1 kΩ) are drawn but not fitted, because the BME280 board already pulls SDA and SCL up to 5 V through 4.7 kΩ.
  - Three 4-pin connectors J1–J3, each 1 = +5V, 2 = GND, then the two signals. Breadboard first (the owner's plan,
    2026-11-09); then a shield PCB that plugs onto the Mega and carries only J1–J3, C2 and the R1/R2 pads. The sensors
    stay on cables. On an R3 board the shield can use the SDA/SCL pins next to AREF and be Uno-sized.
- Rationale: every sensor already outputs numbers (or comes on a board, the HX711, that does), so no analog circuit or
  op-amp is needed (open question 2). Pins 2 and 3 have no special job (0/1 are USB serial, 13 the LED, 20/21 I²C,
  50–53 SPI). Everything runs at 5 V, the BME280 board has its own regulator and level translator, and USB has ample
  current, so the shield needs no chips. A shield keeps the Mega unchanged and swappable.
- Alternatives considered: an external supply (needed only for later extras such as a servo, lights or a mist maker,
  or if USB noise proves to matter; the Mega's barrel jack takes 7–12 V); adding pull-ups now (the bus would sit at
  about 1.9 kΩ with both, still within I²C limits, but unnecessary); a custom board with the ATmega2560 chip itself
  (far harder, no benefit); locking Grove/JST-style connectors for J1–J3 (likely on the PCB; Dupont jumpers on the
  breadboard; owner, 2026-11-17: order them when needed).
- Evidence / source: [SDP8xx](resources/notes/SDP8xx.md), [HX711](resources/notes/HX711.md),
  [TAL221](resources/notes/TAL221.md) and [WaveshareBME280](resources/notes/WaveshareBME280.md) notes; the
  [drawing package](docs/drawings/README.md) sheets 11–12; the
  [walk-through](docs/electronics_walkthrough.md); the
  [2026-11-17 sensor-circuit session](docs/sessions/2026-11-17-sensor-circuit-design.md). Not built or tested. The
  SparkFun HX711 board's pad labels and RATE setting are not yet checked on the delivered board.
- Status: Tentative (agent's design, 2026-11-17). The owner has not confirmed it; the breadboard test (walk-through
  §6) checks it. The PCB program (KiCad recommended, or EasyEDA) is the owner's choice, still open.
  - Note (2026-11-18): the delivered HX711 board labels its bridge pads RED, BLK, WHT and GRN (E+, E−, A−, A+ are the chip's
    names), plus YLW, unused here. The owner built the breadboard's power wiring and it passed (4.962 V); R1 and R2 were

  - Note (2026-11-23, later the same day): the shield PCB is designed, and three details here changed with it

## D-020: Shield PCB: KiCad on the Mega shield template, pin headers for jumper wires, each connector in its part's pin order

- Date: 2026-11-23
- Question: How does the breadboard circuit of D-018 become the shield PCB: which program, which connectors, in what
  pin order, and what goes on the board?
- Decision (the owner drew it; choices made at the computer with the agent checking each save):
  - **KiCad 10.0.7** (owner; answers PROJECT_STATUS open question 18), starting from KiCad's Arduino Mega shield
    template, which places the Mega's headers (P1–P7), its six mounting holes and outlines of the USB socket, power
    jack and ICSP header. Files in `PCB/arduino_shield/`; the manufacturing files in `PCB/arduino_shield/gerbers/`.
  - **J1–J3 are plain 2.54 mm pin headers for Dupont jumper wires** (owner: "i just have general elegoo jumper
    wires"), footprints `PinHeader_1x04` (J1, J2) and `PinHeader_1x05` (J3). Male pins or female sockets fit the same
    holes and can be chosen when soldering.
  - **Each connector follows its part's own pin order, so every cable runs pin 1 to pin 1** (owner: "we prolly wnat
    stright cables"): J1 = SCL, +5V, GND, SDA (the SDP810's pins 1–4); J2 = +5V, GND, SDA, SCL (the Waveshare
    board's header order); J3 = +5V, +5V, HX_DAT (Mega pin 2), HX_CLK (pin 3), GND (the SparkFun HX711 header's VDD,
    VCC, DAT, CLK, GND, top to bottom in the owner's 2026-11-17 photo).
  - **J3 has five pins and joins VDD and VCC to +5V on the shield** (the owner's sketch), so no jumper is needed at the
    HX711 end.
  - **On the shield:** C1 0.1 µF beside J1 (it rode at the cable's board end on the breadboard), C2 10 µF at the 5 V
    entry, R1 and R2 5.1 kΩ as "do not populate" pads, and silkscreen labels naming each connector and its pins.
  - **Board:** the Mega's full size, 101.6 × 53.34 mm, two copper layers, 1.6 mm, 0.25 mm tracks, five vias, no
    ground fill (the agent advised it is not needed at 100 kHz I²C and about 100 mA; the load cell's microvolt signal
    never reaches the shield). The template's duplicate Mega pins (two GND on P1, +5V and GND on P7, SDA/SCL beside
    AREF and on pins 20/21) are all joined in copper, so the shield does not rely on the Mega linking them inside.
  - **C1's and C2's footprints are placeholders** (`C_Disc_D5.0mm_W2.5mm_P5.00mm`,

  full-size template places every header and hole correctly for a beginner.
- Alternatives considered: sheet 12's uniform order (1 +5V, 2 GND, 3–4 signals) with hand-crossed cables; a separate

  solder bridge between the HX711's VDD and VCC pins; locking JST PH or Grove-style plugs (D-018's suggestion; the

## D-021: Capture serial data to CSV with `scripts/serial_capture.ps1` (PowerShell), stamped with the PC's clock

- Date: 2026-11-26
- Question: How does data from the Mega reach a file? The Arduino IDE's Serial Monitor copies only the lines on screen,
  so minutes of HX711 data for EXP-002 (and later every tunnel run) could not be kept by copy and paste.
- Decision (agent's choice while the owner was at the bench):
  - `scripts/serial_capture.ps1` opens the port (COM3, 115200 baud), writes every line the board sends to a new CSV file,
    unchanged except for a `pc_time` column in front (the PC's local time, ISO 8601 with milliseconds and UTC offset),
    flushes each line to disk at once, and stops on Ctrl+C, after `-Seconds`, or when a `-StopFile` appears.
  - It refuses to overwrite an existing file and opens the port before creating the file, so `data/raw/` is never
    overwritten and a busy port leaves nothing behind.
  - It uses Windows PowerShell 5.1 and .NET's `System.IO.Ports.SerialPort`, both part of Windows. This is an exception
    to "helper scripts are Python standard library only" (CLAUDE.md), because the standard library has no serial port
    and the alternative, pyserial, is an install.
  - Opening the port resets the Mega, so each file starts with the sketch's messages and header; buffer leftovers from
    before the reset may come first and are skipped by the analysis. The Arduino IDE must be closed (it holds the port).
- Rationale: nothing to install; no lost lines; the PC time lines the data up with notes of what was done when; the board's
  own `time_ms` column is kept for the sample timing.
- Alternatives considered: copying from the Serial Monitor in chunks (loses lines); printing one averaged line every
  10 s so a run fits on screen (loses information); Python with pyserial (an install); a Python ctypes serial reader
  (long, untested code); a terminal program with logging such as PuTTY (an install, and no time stamps by default).
- Evidence / source: used for EXP-002 run02, 20,180 lines over 32 min with a steady 95 ms interval
  ([data catalog](docs/data_catalog.md#exp-002-load-cell-on-the-printed-bench-scale)); run01 is the empty file left
  by the first version, which created the file before opening the port. No automated test.
- Status: Tentative (agent's choice, 2026-11-26; the owner has not confirmed it).
