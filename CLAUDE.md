# Wind Tunnel: instructions for AI agents

A small wind tunnel with home-built instrumentation (pitot tube + differential pressure sensor for airspeed,
load cell + HX711 for drag). The tunnel is validated by measuring a sphere's drag coefficient against the published
value (~0.47) before any other result is trusted. Owner: Nuh Shaheer. The project is in the **planning / pre-build**
stage; check `PROJECT_STATUS.md` for the current state.

The documentation is the project's memory. Assume the next agent has none of your conversation. Anything not written
into these files is lost.

## Hard rules

1. **Never run `git push`** (or anything that pushes: `gh pr create`, `gh repo sync`, force-push, etc.). The owner
   pushes every change manually. `.claude/settings.json` denies `git push` for agents; do not work around it.
2. **Never commit unless the owner explicitly authorizes it** in the current session (e.g. `/wrap commit`). Default:
   leave changes uncommitted and give the owner exact commands.
3. **Never use destructive Git commands:** no `reset --hard`, `checkout -- <file>`, `restore` on others' work,
   `clean -f`, `stash drop`, `rebase` of published history, or `--force` anything.
4. **Never edit, rename, move or delete anything in `data/raw/`.** Processed data is regenerated by scripts, never hand-edited.
5. **Never invent** measurements, sensor specs, equipment settings, results, citations or completed work. Unknown values stay "Unknown".
6. **Never commit secrets** (tokens, keys, passwords, `.env`) or files over 25 MB without following DECISIONS.md D-004.

## Reading order (also what `/catchup` does)

1. `CLAUDE.md` (this file)
2. `PROJECT_STATUS.md`: authoritative current state
3. `TODO.md`: what to do next
4. `PROJECT_BACKGROUND.md`: goals, physics, constraints, uncertainty sources
5. `DECISIONS.md`: why things are the way they are
6. `docs/experimental_setup.md`: the physical setup as built
7. `docs/data_catalog.md`: every dataset and how it was processed
8. `docs/sessions/SESSION_LOG.md`, then the newest one or two session logs

## Commands

- **`/catchup`** (start of session): safely fetch from GitHub and fast-forward only if safe, read the docs, check them
  against the actual files, flag discrepancies, report a handoff summary and the first task.
  Procedure: `.claude/skills/catchup/SKILL.md`.
- **`/wrap`** (end of session): audit the whole project, update every doc that needs it, write or update this session's
  log, run the checks, and give the owner exact commit-and-push commands. `/wrap commit` additionally authorizes one local
  commit. Procedure: `.claude/skills/wrap/SKILL.md`.

Both are plain Markdown procedures, so an agent without slash-command support can read the file and follow it.

## Helper scripts and tests (Python 3 standard library only)

```bash
python scripts/sync_status.py --fetch          # where local stands vs GitHub (read-only apart from fetch)
python scripts/sync_status.py --fetch --pull   # also fast-forward when strictly behind and safe
python scripts/check_docs.py                   # documentation consistency, size and secret checks

```

## Documentation rules

- **Status labels** for work and results (use exactly): Verified, Implemented, unverified, Preliminary result,
  In progress, Planned, Blocked, Tentative. Code existing does not mean the experiment worked. Verified needs a
  measurement, test or calibration you can point to. Parts inventory uses its own words (On hand, To buy, Unknown).
- `PROJECT_STATUS.md` is a concise snapshot of *now*; detailed history goes in session logs. Update its
  `**Last updated:**` line whenever you change it.
- One session log per working session: `docs/sessions/YYYY-MM-DD-short-topic.md`, listed once in
  `docs/sessions/SESSION_LOG.md`. Rerunning `/wrap` in the same session updates the same log. Never delete or rewrite
  old logs (filling in a missing commit hash is fine).
- `DECISIONS.md`: append-only. Supersede old decisions instead of deleting them.
- Record **failed experiments and dead ends** in the session log (and in the data catalog if data was taken). They are results too.
- Record **uncertainty** with every number: units, how it was measured, error estimate or "not quantified".
- Separate raw observation → processed result → interpretation. Do not state a scientific conclusion the data does not support.
- Every result must point to its raw data, the script and the command that produced it.

## Engineering conventions

- SI units everywhere (Pa, m/s, N, m, kg, K or degC stated). Units in CSV column names: `time_s,dp_Pa,force_N`.
- Analysis code goes in `analysis/`, reads from `data/raw/` or `data/processed/`, and writes to `data/processed/` or
  `results/`. Each script states inputs, outputs and units at the top. Do not hard-code calibration constants without
  citing the calibration dataset.
- Data layout and naming: `data/README.md`. Videos stay out of Git; reference them from the data catalog.
- Reference papers go in `resources/` with a notes file in `resources/notes/`; naming, notes template and index are
  in `resources/README.md`. Read a paper's notes before opening its PDF, and cite the notes file when a paper informs
  a design choice.
- Run the tests and `scripts/check_docs.py` before finishing any session that changed code or docs.
- Commit messages: imperative summary line (≤ 72 chars), body explaining why.
- Physical checks (calibrations, equipment tests) cannot be done by an agent. If one is needed, say so and list it as
  an owner task; never mark it done without the owner's reported result.
